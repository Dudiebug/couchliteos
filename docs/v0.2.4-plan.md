# CouchLiteOS 0.2.4 plan

Theme: everyday control from the couch. Keyboard keys that do what they say, a Home shortcut
on any controller, adjustable pointer speed, an on-screen keyboard that leaves the app visible,
and a faster build so releases ship sooner.

## 1. Brightness and volume keys

**Problem:** the brightness and volume keys on a keyboard do nothing. Nothing in the system
reads them, and Cage does not handle them itself.

**Plan:**
- gamepad-nav already reads every keyboard to catch the Super key. It will also handle
  `KEY_BRIGHTNESSUP/DOWN`, `KEY_VOLUMEUP/DOWN` and `KEY_MUTE`, including the Apple Fn layer.
  Keyboards plugged in later are picked up the same way pads are.
- **Brightness** goes to `/sys/class/backlight`.
  - It picks the device in the same order systemd uses: firmware, then platform, then raw.
  - Steps are 5% each on a curve, with a 5% floor so the screen never goes fully dark.
  - A udev rule gives the launcher's group write access to the brightness file, so no new
    root service is needed. systemd-backlight already restores the level after a reboot, and
    the updater keeps it.
- **Volume and mute** use the same `couchliteos_audio` path as the Guide menu, so both stay in
  step.
- **Guide menu:** a `BRIGHTNESS  NN%` row next to VOLUME, changed with left/right. It is hidden
  on PCs with no adjustable backlight.
- **Stretch goal:** external monitors through DDC/CI (`ddcutil`, `i2c-dev`) when there is no
  backlight. It ships only if it is reliable on test hardware; otherwise it moves to a later
  release.
- **Tests:**
  - Device choice, step curve and floor against a fake sysfs.
  - Key events against a fake evdev keyboard, including Fn variants and hot-plug.
  - The Guide menu row is hidden when nothing can be adjusted.
  - A static check for the udev rule.

## 2. Home shortcut for controllers and keyboards

**Problem:** only Guide and Super open Home. Many pads have no usable Guide button: some
Bluetooth pads, generic pads, and pads where Steam or Windows-style drivers grab it. Some
keyboards have no Super key, or the user does not expect it to open Home.

**Plan:**
- **Controller:** hold **SELECT + START for 1.5 s** to open Home. A hold avoids clashing with
  games, and it never overlaps Moonlight's own Select+Start+L1+R1 quit combination.
- **Keyboard:** **Ctrl + Alt + H** opens Home, in addition to a Super tap. Unlike Super, it
  also works during a Moonlight stream or remote desktop session: it is the keyboard's way
  home from one. The volume keys likewise keep controlling this box's (the TV's) volume.
- With SELECT+START as the shortcut, SELECT's and START's own actions (launcher shortcuts,
  Esc/Space for the controller mouse) happen on release, and only for a lone tap.
- **Settings > Controls > HOME SHORTCUT:**
  - Choices: `GUIDE ONLY` / `GUIDE OR SELECT+START (HOLD)` (default) / `GUIDE OR L3+R3 (HOLD)`.
  - The keyboard shortcut can be turned off.
  - The CONTROLLER BUTTONS help screen shows the current shortcut.
- It goes through the same Home event as Guide, so it works over a running app exactly as
  Guide does since 0.2.3.
- **Tests:** combo timing (a hold opens Home, a tap does not, and releasing early cancels),
  each setting, Ctrl+Alt+H per keyboard, and no Home event while a combo key is held for other
  input.

## 3. Pointer speed

**Plan:**
- **Controller mouse speed:** Settings > Controls > CONTROLLER MOUSE SPEED with
  `SLOW / NORMAL / FAST / VERY FAST`. It scales `stick_curve()`'s top speed and takes effect
  live, because gamepad-nav re-reads the setting file.
- **Mouse and touchpad speed:**
  - Settings > Controls > MOUSE SPEED, using the same four steps mapped to libinput
    acceleration speed.
  - Cage cannot set this today, so the existing Cage patch set gains a small patch.
  - The patch reads a speed file when an input device is added, and re-applies it to all
    devices on `SIGHUP`. The launcher sends `SIGHUP` after the setting changes.
- **Tests:**
  - The speed table, live re-reading in gamepad-nav, and the settings rows.
  - A static check that the patch applies against the pinned Cage source.
  - A VM check that libinput reports the new acceleration speed.

## 4. What's New shows only this release

**Problem:** after an update, the screen showed earlier releases' changes too. It lists every
release newer than the last version seen, so a missed or old marker produces a long history.

**Plan:**
- Show only the release you are now on, with "EARLIER CHANGES: SEE THE RELEASE NOTES" when
  there is history.
- Keep the version guard that fails the build when `RELEASES[0]` is not the version being
  built.
- Add a test that an upgrade from any older version shows exactly the current release's lines.

## 5. On-screen keyboard must not cover the whole screen

**Problem:** the keyboard is a full-screen terminal window (`couchliteos_osk.py`: "Full-screen
buffered controller keyboard"). Cage makes every window full-screen, so the app you are typing
into disappears behind it.

**Plan:**
- Dock the keyboard as a panel along the bottom, at most 40% of the screen height, with the app
  still visible and live above it.
- Approach, in order of preference:
  1. A layer-shell panel, if the pinned Cage supports wlr-layer-shell. This is checked first in
     the VM.
  2. Otherwise, a small Cage patch that places the window with app-id `couchliteos-osk` as a
     bottom-anchored overlay instead of maximising it.
- Typing, masking, the 512-character cap and keyboard injection stay as they are. Only where
  the keyboard is drawn changes.
- The keyboard's draw code is laid out for a short panel: the 4 letter rows plus 2 action rows
  fit in about 12 terminal rows.
- **Tests:**
  - The layout fits the panel at 720p, 1080p and 4K.
  - A static check for the app-id and the patch.
  - A VM screenshot (`grim`) of Cage running a test app with the keyboard open. The test app
    must still be visible in the top 60% of the screen.

## 6. Faster builds

**Measure first:** add per-stage timings (bootstrap, chroot, packages, tests, binary, squashfs)
to the build log, and record a baseline.

**Then:**
1. **apt-cacher-ng in the build VM.**
   - All .deb and installer files come from local disk.
   - Files are checked against Debian's index hashes, so the two corrupt cached packages that
     broke the 0.2.3 builds cannot recur.
   - It replaces the plain package cache.
2. **Reuse the chroot stage** (live-build stage cache). It is rebuilt only when the package
   lists, hooks or apt sources change, keyed on their hash.
3. **zstd squashfs for test builds.** xz stays for release builds (`--release`).
4. **Skip the duplicate test run.** The build skips the unit and static suite when a marker
   shows that commit already passed `make test`.
5. **Verify cached packages before a build:** `dpkg-deb --fsys-tarfile` on each cached file, and
   delete any bad ones.
6. **Debian installer files:** check whether the ISO uses debian-installer at all. Drop them if
   CouchLiteOS's own installer does not need them.
7. **Package versions:** make the Tailscale version agree between the package list and the
   notices (1.102.3 is listed, but the build upgrades to 1.102.4). Pinning a dated
   snapshot.debian.org mirror is evaluated, but only adopted if it is not slower.

**Goal:** a repeat build with no package changes takes well under half of today's time. The
before and after numbers go in the release notes.

## Also in 0.2.4

- **Docs:** a troubleshooting entry for a black stream from a host with no monitor. Sunshine's
  display list is empty and the desktop is 1024x768; the fix is a dummy plug or a virtual
  display driver. Also recommend ViGEmBus for controller input on Windows hosts.

## Completion gate

1. Every item above is implemented with tests. The only optional part is the DDC/CI stretch
   goal in item 1.
2. `make test` passes in full in the build VM.
3. Three review passes are run, and every finding is fixed.
4. The ISO is built with the new fast build path, and the build times are recorded.
5. The ISO boots in a VM: Home shortcut, What's New, and a keyboard screenshot.
6. The release notes are written, and the What's New lines are at most 66 columns.
7. Push `release/0.2.4` and publish v0.2.4 as the latest release.
