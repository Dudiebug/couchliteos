# CouchLiteOS v0.1.9 release specification

Status: locked before implementation on `codex/fix-installer-regression`.

Spec approval was not obtained because this is an explicitly unattended run. The
requested acceptance criteria below are therefore the reviewable contract, and
confidence must be downgraded anywhere the final evidence cannot prove them.

## Outcome

Publish one immutable `0.1.9` release whose ISO boots through real x86_64 UEFI
firmware and its on-disc boot menu, completes a destructive install to an empty
32 GiB virtual disk, boots without the ISO, reaches the CouchLiteOS launcher,
and retains test state across a cold reboot. The boot menu and text installer
must use the same black, white, high-contrast visual language as the launcher
without removing keyboard navigation, serial logging, rescue entries, or text
fallbacks.

The `0.1.6` and `0.1.8` tags and releases are immutable reference artifacts.

## Setup plan

- Use only the existing Debian live-build, shell, Python standard library,
  QEMU/OVMF, xorriso, and GitHub Actions toolchain. Add no runtime dependency.
- Prefer a Hyper-V Generation 2 VM with 4 vCPUs, 4 GiB RAM, a blank 32 GiB
  VHDX, Secure Boot disabled, and the Microsoft UEFI CA template when the host
  supports it. Otherwise use an equivalent QEMU q35/OVMF VM and still boot the
  ISO as removable media through firmware and its boot menu.
- Treat VM storage-backend failures as laboratory failures until reproduced on
  a second backend. Never patch CouchLiteOS to hide a corrupt virtual disk.
- Build and test the exact artifact that will be uploaded. After upload,
  download that asset again and repeat the install test before publishing.
- Keep all generated disks, screenshots, logs, artifact manifests, and release
  readbacks outside the source tree; commit only reusable tests and reports.

## Failure model (Tier 3)

| Failure | Required control |
|---|---|
| A test bypasses the release bootloader by loading an extracted kernel/initrd | The install smoke test must attach the built ISO, start at OVMF, select the ISO's installer menu entry, and reject `-kernel`/`-initrd`. |
| The installer targets the wrong disk or corrupts an existing disk | Use a newly created disposable 32 GiB disk and assert its pre-install emptiness and post-install partition/filesystem identity. |
| The boot-menu rewrite changes installer arguments beyond the requested dark theme, duplicates entries, loses permissions, or is non-idempotent | Fixture tests permit only `theme=dark`, assert entry counts/order and modes, and run the hook twice. |
| Styling makes a selected item, help, rescue path, or serial fallback unreadable/unreachable | Static config assertions plus captured UEFI-menu and installer screenshots; retain advanced, rescue, utilities, keyboard, and serial paths. |
| Install appears successful but the disk is not independently bootable | Detach the ISO, cold boot the disk, require launcher and service health markers, then cold boot again and require persisted state. |
| Diagnostics are insufficient to explain a failure | On failure upload serial log, firmware/boot-menu screenshot, installer screenshot, QEMU configuration, and disk metadata. |
| The wrong bytes are published, or a tag/release races with another build | Pin tag target to the merged commit, publish a draft first, compare local/upload/public SHA-256 and byte count, and verify source archives against the tag. |
| A passing result is stale or from pre-fix source | One final fail-closed gauntlet deletes stale reports and records the source-state hash before all reported evidence. |

## Executable scenarios

```gherkin
Feature: CouchLiteOS v0.1.9 release integrity
  Scenario: Reference artifacts are authentic and immutable
    Given the official 0.1.6 and 0.1.8 release URLs and source tags
    When their assets and source archives are downloaded
    Then URLs, filenames, byte counts, and SHA-256 values are recorded
    And each source archive has the same relative-file SHA-256 map as its tag
    And neither historic tag nor release is modified

  Scenario: Boot-menu transformation preserves installer behavior
    Given representative generated GRUB and ISOLINUX configurations
    When the binary boot hook runs twice
    Then live, no-persistence, install, advanced, rescue, and utility paths remain
    And each entry occurs exactly once in the intended order
    And only the explicit theme=dark installer argument changes
    And the installer kernel, initrd, and every other argument are unchanged
    And transformed files retain their original modes

  Scenario: Built ISO installation follows the public boot path
    Given the built ISO, UEFI firmware, and a blank 32 GiB disposable disk
    When the VM boots the ISO and selects its visible installer menu entry
    Then the test never passes an extracted kernel or initrd to QEMU
    And the installer completes without filesystem, partman, or bootloader errors

  Scenario: Installed system survives independent cold boots
    Given the completed installation and detached ISO
    When the disk is cold-booted twice
    Then the launcher readiness marker appears on both boots
    And state written on the first boot is read on the second

  Scenario: Boot interfaces match the launcher visual language
    Given a real UEFI ISO boot and the Debian text installer
    When their primary and selected states are captured
    Then backgrounds are black, foreground text is white and high contrast
    And spacing, borders, selection, and accent treatment are consistent
    And keyboard help, advanced/rescue entries, and serial output remain available

  Scenario: Published asset is the tested asset
    Given the merged commit, 0.1.9 tag, draft release, and locally tested ISO
    When the draft asset is downloaded and installed and the release is published
    Then local, draft-download, and public-download byte counts and SHA-256 match
    And the public source archive matches the tagged source tree
    And a final fresh public-download installation passes
```

## Spec-to-test map

| Scenario | Automated evidence |
|---|---|
| Reference artifacts are authentic and immutable | `tools/release-evidence.sh provenance` plus recorded GitHub readback |
| Boot-menu transformation preserves installer behavior | `tests/test-static.sh` boot-hook fixture |
| Built ISO installation follows the public boot path | `tests/qemu-install-smoke.sh` |
| Installed system survives independent cold boots | `tests/qemu-install-smoke.sh` |
| Boot interfaces match the launcher visual language | config assertions and captured screenshot review |
| Published asset is the tested asset | `tools/release-evidence.sh artifact` plus draft/public install logs |

## Acceptance gate

No release may be described as finished if any required test fails, is skipped,
or exercised different ISO bytes. Every skip is reported as unverified, never
as a pass. Publishing is the final mutating step and occurs only after the exact
draft asset completes its own installation test.
